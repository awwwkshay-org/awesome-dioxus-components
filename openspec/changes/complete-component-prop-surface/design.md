## Context

See `proposal.md` — Why for the motivating evidence. All counts in this
document are measured directly against `statics/prop_parity/*.json` (as
regenerated by Change A, `extend-upstream-prop-evidence`, including its
`attributes: Vec<Attribute>`-extends coverage fix) and the current
`registry/ui/*.rs` source, not assumed or carried over from an earlier,
unverified pass.

Relevant existing pieces:
- `statics/prop_parity/<item>.json` (Change A): per item, per axis,
  `matchedComponent` + per-part `props: [{name, status, reason?}]`, where
  `status` is `present | missing | intentional_difference |
  adico_extension`. `adico_extension` reasons live in a fixed `const`
  table in `packages/adico-xtask/src/prop_parity.rs`, keyed by `(item,
  part, prop)`, joined in at `sync` time — this is the mechanism `radius`
  and `loading` (Decisions D3/D4) register into, not a new one.
- `registry/lib/cn.rs`: a plain filter+join, not tailwind-merge — no
  class-conflict resolution. A `radius` prop emitting `rounded-full`
  alongside a base string that already contains `rounded-md` yields two
  competing classes resolved only by Tailwind's own source order, not by
  this project's code. `radius` must therefore own `rounded-*` outright,
  not be layered on top of it.
- Fourteen registry files already establish the `enum FooVariant/FooSize`
  + `impl FooVariant { fn class(self) -> &'static str }` inherent-impl
  convention `Radius` follows.
- The five existing per-component size enums, confirmed unchanged:
  `ButtonSize { Default, Xs, Sm, Lg, Icon, IconXs, IconSm, IconLg }`,
  `AvatarSize { Sm, Default, Lg }`, `NativeSelectSize { Default, Sm }`,
  `SwitchSize { Sm, Default }`, `ToggleSize { Sm, Default, Lg }`.
- `registry/ui/slider.rs`'s own code comment (verified current): *"
  `SliderProps`/`RangeSliderProps` have no dedicated `class` field (only
  `attributes: Vec<Attribute>`, extending `GlobalAttributes`), and a
  `class` keyword can't be mixed with a `..props` struct spread at a
  *component* call site"* — both props types are `pub use
  adico_primitives::slider::{RangeSliderProps, SliderProps}` re-exports
  verbatim, so the registry facade has no type of its own to add a field
  to; the fix has to land in the primitive.
- `grep`-verified current state: 50 of 66 registry files use a `rounded-*`
  Tailwind class; 0 of 66 declare a `radius`-typed rounding-control prop
  (`theme_builder.rs`'s own `radius: String` field is a CSS
  custom-property *value* editor, an unrelated concept, not a
  per-component prop); 0 of 66 declare `loading`; 8 of 66 declare
  `variant`; 5 of 66 declare `size`; 25 of 66 already declare
  `attributes: Vec<Attribute>` with `#[props(extends = ...)]`.

## Goals / Non-Goals

**Goals:**
- Close every evidence-backed upstream gap `prop-parity` records, either
  by implementing the prop or by reclassifying it `intentional_difference`
  with a written reason — never left silently `missing`.
- Ship `radius` and `loading` as clearly-labeled `adico_extension` props
  with recorded reasons, not presented as upstream parity.
- Name and hand-verify each convention-normalization rule against real,
  current source before applying it at scale — the same discipline Change
  A's alias table and reason tables used, not a blanket heuristic.
- Preserve the source-distribution model: every fix lands in
  `registry/ui/*.rs` or `packages/adico-primitives/src/*.rs`, propagated
  to consumers only through `adico add --replace`.

**Non-Goals:**
- No shared `Size` enum. See Decision D1.
- No `as_child`/merge-props support — Dioxus has no mechanism (already
  documented at `packages/adico-primitives/src/field.rs:6` and three
  registry module docs).
- No tailwind-merge port of `cn()` — solved by removing `rounded-*` from
  base strings instead (Decision D3); revisit only if that proves
  insufficient.
- No new registry items beyond `variants` — this change completes props
  on the existing 66, it does not grow the catalog.
- No change to `adico-cli` or `adico-registry-core`.

## Decisions

### D1: Ship `Radius` only; reject a shared `Size` enum

`ButtonSize`'s four icon-square sizes (`IconXs`, `IconSm`, `Icon`,
`IconLg`) have no slot in a generic `Size` scale shared with e.g.
`AvatarSize`'s three plain sizes. More importantly: this is a
**source-distribution** ecosystem (consumers copy and own the source), so
renaming `ButtonSize::Default` → `Size::Md` breaks every consumer's own
call sites on their next `adico add --replace` — a breaking rename with no
functional benefit, since each component's size scale is genuinely
different. New size-related parity props in the D5 waves keep the
existing per-component `<Comp>Size` convention. A shared scale, if ever
wanted, is its own `**BREAKING**`-marked change with a migration note, not
a side effect of this one.

`Radius` is different: every component that has one wants the *same*
scale (`None`/`Sm`/`Default`/`Lg`/`Xl`/`Full`, `Default` tracking the
`--radius` CSS custom property `theme_builder.rs` already manages), and no
component currently has *any* radius-control prop to conflict with —
there is nothing to migrate away from.

### D2: Convention normalization — one named rule per inconsistency, each hand-verified against current source

- **`disabled`**: one representation per component *category* —
  native-leaf components (render a real native element directly, e.g.
  `Input`, `Textarea`) use `Option<bool>`; primitive-backed components use
  `ReadSignal<bool>` (matching the primitive's own controllable-prop
  convention). `Button`'s native-only routing (no primitive backing it)
  stays as the intentional category-1 case, documented not "fixed".
  Implementation surfaced a second, narrower exception per the Risks
  section's own mitigation discipline: `SidebarMenuButton` is genuinely
  native-leaf (renders a real `button`) and was `bool`, not `Option<bool>`
  — fixed to match its category, no exception needed. `Item` renders a
  `div`, which has no native HTML `disabled` attribute at all to mirror —
  its disabling is entirely synthetic (`aria-disabled` + a manual
  `onclick` guard), so it doesn't fit either category and stays a plain
  `bool`, documented in its own doc comment as this rule's second
  exception.
- **`class: Option<String>` on every styled component.** Closes `Slider`,
  `RangeSlider`, `Toast`, `AreaThumb`, `HueSlider` (verified: `AreaThumb`
  and `HueSlider` take no `class` parameter at all;
  `Slider`/`RangeSlider`/`Toast` re-export the primitive's props type
  verbatim with no class field). For a facade that is a bare `pub use
  primitive::FooProps` re-export, the field is added to the *primitive*
  (this repo has already authorized primitive changes for this effort),
  so the facade keeps being a re-export rather than becoming a
  registry-owned wrapper struct that would diverge from the primitive's
  own type over time.
- **`#[props(extends = GlobalAttributes)]` + `attributes: Vec<Attribute>`**
  on every styled component that renders a real element: 25 of 66 already
  have it; extend toward the remainder identified in the D5 waves. `class`
  stays a **separate** field, never folded into `attributes` —
  `registry/ui/sidebar.rs`'s `SidebarProviderProps.class` doc comment
  records the live layout-collapse bug that made this its own rule, not a
  style preference.
- **Restore dropped props**: `Checkbox`'s form `value` + `attributes`
  (currently narrowed relative to its primitive); `ToastProvider`'s
  `default_duration`/`max_toasts` un-narrowed back to `ReadSignal<...>` so
  a consumer can reactively change them, matching the primitive's own
  type.
- **Handler naming**: `onclick`/`oninput` (no separator) for
  native-element-mirroring leaves; `on_*_change`/`on_select` (adico's own
  snake_case semantic-callback convention) for primitive-facing
  components. Verified current violations: `AlertDialogAction`/
  `AlertDialogCancel` (`on_click: Option<EventHandler<MouseEvent>>`) and
  `ToolbarButton` (`on_click: Callback<()>`) are both primitive-facing yet
  use the React-style `on_click` name — renamed to fit their category
  (e.g. `on_select`/a component-appropriate semantic name), not left as a
  third convention.
- **`**BREAKING**` controlled-trio**: standardize on
  `ReadSignal<Option<T>>`. Verified against current source: the
  originally assumed "5 holdouts" is actually **3 items** —
  `Select`/`Combobox`/`TagGroup`'s *singular*-select function each
  declares `value: Option<ReadSignal<Option<T>>>` (double-`Option`); their
  own `SelectMulti`/`ComboboxMulti`/`TagGroupMulti` functions already use
  the target single-`Option` `values: ReadSignal<Option<Vec<T>>>` shape.
  Migrate the 3 singular functions to match; if a specific case turns out
  to need the double-`Option` for a real reason during implementation,
  record it `intentional_difference` with that reason rather than forcing
  the migration blindly.

### D3: `radius` rollout — strip `rounded-*` from base strings *and* every variant/size class function, enforced by a real test

`radius: Radius` is added to every component with a visible bounded
surface (the population overlaps heavily with, but is not identical to,
the 50 files that already hard-code `rounded-*` — a component with no
visible bounded surface at all, if any exist among the 50, is excluded
with a recorded reason rather than force-fit).

The strip is **not only in base class strings**: in
`registry/ui/button.rs`, `rounded-md` lives inside `ButtonSize::class()`
(`Xs => "h-6 gap-1 rounded-md px-2 text-xs"`, similarly `Sm`/`Lg`/
`IconXs`/`IconSm`/`IconLg`), the same shape recurring across the 14 files
with an `impl … { fn class(self) }`. Missing the per-variant/size copy
would leave a competing hard-coded class `cn()` cannot resolve (Context).

Verification is a real, CI-gated test, not a one-off grep: a new unit test
in `packages/adico-xtask/src/styling_usage.rs` asserts no `rounded-`
literal appears anywhere in a radius-bearing item's `registry/ui/*.rs`
file outside `Radius::class()`'s own match arms — condition (g), following
the existing lettered-condition pattern (a)–(f) that file already uses.

`radius` is an adico extension exactly like `loading` (D4), so it must
register the same way: one `(item, part, prop)` entry per radius-bearing
item added to `prop_parity.rs`'s `ADICO_EXTENSION_REASONS`, naming the
part the `radius` prop actually lands on for that item (its single root
part for a single-part item; the specific part that owns the rounded
surface for a multi-part item, e.g. `PopoverContent`'s `content` part, not
`PopoverTrigger`). Without this, `radius` shows up in zero
`prop_parity` records after rollout — neither `missing` nor
`adico_extension` — which would silently contradict this document's own
Context claim that `radius` registers into that table. The reason string
is "adico extension: consistent corner-radius control not present
upstream" (or the component-appropriate equivalent). Task 3.1 produces
this per-item `(part, reason)` mapping alongside its target list, the same
way task 4.2 does for `loading`'s seven items.

### D4: `loading` is composed over `Spinner`, never a duplicated icon

`loading: bool` + `loading_text: Option<String>` on the seven actionable
components (`Button`, `InputGroupButton`, `PaginationLink`,
`AlertDialogAction`, `ToolbarButton`, `SidebarMenuButton`, `DataTable` —
all seven verified to exist as named functions in their respective
files). Implementation declares `spinner` in `registryDependencies` and
composes the existing `Spinner` registry item; setting `aria-busy` and
native `disabled` while loading. This is a deliberate adico extension —
shadcn's own convention is `<Button disabled><Spinner /></Button>`
composed by hand at each call site — recorded as `adico_extension` with
that exact reason in each of the seven items'
`statics/prop_parity/<item>.json`, via `prop_parity.rs`'s
`ADICO_EXTENSION_REASONS` table (currently empty; this change is its
first real entries).

### D5: Parity-prop waves, grouped by relationship, driven by real evidence

Grouped by structural relationship rather than an arbitrary fixed size,
following the precedent of `docs/adico/m3-wave{1..5}-migration.md` (waves
of 4–16 items grouped by dependency/category, not a fixed count). Every
count below is `statics/prop_parity/*.json`'s `missing` entries for that
item's best-matching axis (25 of 66 items — `alert`, `aspect-ratio`,
`badge`, `breadcrumb`, `button-group`, `card`, `carousel`, `collapsible`,
`data-table`, `date-picker`, `empty`, `input-group`, `kbd`, `message`,
`message-scroller`, `mode-toggle`, `native-select`, `resizable`,
`scroll-area`, `skeleton`, `spinner`, `table`, `theme-builder`,
`theme-switcher`, `virtual-list` — have zero and need no D5 work beyond D2
convention normalization and D3/D4 rollout):

| Wave | Theme | Items (missing-prop count) | Total |
|---|---|---|---|
| 1 | Composite/collection controls | combobox (29), slider (26), select (16), calendar (14), navigation-menu (11) | 96 |
| 2 | Menu/overlay family | dropdown-menu (5), hover-card (5), context-menu (3), menubar (3), popover (6), tooltip (6), toggle-group (6) | 34 |
| 3 | Native leaf/form controls | checkbox (7), switch (6), progress (6), toggle (1), input (2), textarea (2), toolbar (2), avatar (2), accordion (1), button (1), label (1), radio-group (1) | 32 |
| 4 | Dialog/overlay content | sheet (6), dialog (3), alert-dialog (3), drawer (3), command (3) | 18 |

41 items, 228 total gaps. `tasks.md` names each wave's items and total but
does not hand-copy all 228 individual prop names into a markdown file —
`statics/prop_parity/<item>.json` is the exhaustive, generated source of
truth for exactly which props each item needs; tasks.md points at it
rather than duplicating it, the same relationship `component_compat.rs`
already has with `statics/catalogs/*.json`.

Wave 1's `combobox`/`slider`/`select` account for 71 of the 228 gaps
(31%) — mostly native form-integration props on their `root` part
(`name`, `form`, `required`, `readOnly`/`read_only`, `min`/`max`/`step`
for `slider`) and Base UI's newer collection-management props
(`items`/`isItemEqualToValue`/`itemToStringLabel` on `combobox`) that
didn't exist when these components were first built. This wave is
correctly the largest and hardest, not an artifact of double-counting —
confirmed by cross-checking against the "genuine gap, not normalization
noise" scenario below.

### D6: A `missing` entry is never left silently unresolved

Every entry `prop-parity` currently classifies `missing` for one of the 41
items ends this change as one of: implemented (the common case), recorded
`intentional_difference` with a written reason (e.g. a Base UI
collection-virtualization prop with no Dioxus-idiomatic equivalent yet),
or named as an explicit follow-up block with a reason it can't land in
this change (e.g. a genuine primitive-behavior gap requiring new
`adico-primitives` work beyond a prop rename). `tasks.md`'s wave sections
each end with a "Verify every `missing` entry for this wave's items is
resolved" step naming `prop-parity diff` as the mechanical check — a wave
is not done while `prop-parity diff` still reports drift for its items
against what the updated source should produce.

## Risks / Trade-offs

- [Bulk registry changes across most of 66 files risk breaking installed
  consumer fixtures in ways a single-item change wouldn't surface] ->
  Mitigated: `examples/basic-spa`/`examples/basic-ssr` and
  `tests/installation/*` are refreshed and rebuilt (`cargo check`/`cargo
  test`) after each wave, not only once at the end, so a break is
  attributed to its wave.
- [The `**BREAKING**` controlled-trio migration (D2) changes 3 items'
  public prop types] -> Accepted and labeled per this repo's own
  `**BREAKING**` convention (used by `improve-existing-components` and
  `reauthor-primitives-from-independent-spec`); lands through the normal
  `adico add --replace` path, the same mechanism any registry source
  change already requires consumers to use to receive updates.
- [D5's wave sizes are uneven (18 to 96 missing entries) rather than a
  uniform ~10-item chunk] -> Accepted: grouping by relationship (so one
  implementer's context — e.g. Base UI's collection-management API — is
  reused across a wave) is worth more than uniform chunk size, matching
  the M3 wave precedent's own reasoning.
- [A convention-normalization rule (D2) turns out to have an exception
  this document didn't anticipate once implementation starts on a
  specific component] -> Mitigated: D2 already states `Button`'s
  native-only `disabled` routing as one documented exception; the same
  discipline (name the exception, don't silently deviate) applies to any
  new one found, recorded in that component's own doc comment plus a note
  in this file if the exception is structural enough to affect other
  components too.

## Open Questions

None — the shared-vocabulary decision (D1), every convention rule (D2),
the `radius`/`loading` rollout mechanics (D3/D4), the wave grouping (D5),
and the resolution discipline (D6) are the load-bearing decisions and are
resolved above. Any component-specific judgment call surfaced only during
implementation (an unanticipated exception, a genuinely ambiguous
`missing` entry) is resolved in that item's own wave task, per D6, not
deferred as an open question here.
