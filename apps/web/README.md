# adico's public site

The landing page, docs, and component playground, served from one Dioxus
app and router: `/` (landing), `/docs/*` (usage/accessibility/keyboard docs
for every registry component), and `/playground/*` (an interactive explorer
for every component currently migrated into the adico registry). Every
component is installed the same way a real consumer would install them: via
`adico add`, not a direct workspace import of `adico-primitives`/`registry`.

## Structure

- `src/pages/index.rs` — the landing page (`/`).
- `src/pages/docs/` — the docs route tree (`/docs`, `/docs/components/:name`),
  reading `registry/registry.json` and `statics/component_props.json`.
- `src/pages/playground/` — one file per routed playground page component
  (e.g. `button.rs` -> `ButtonPage`, `dialog.rs` -> `DialogPage`), named
  after its route's path segment under the `/playground/` prefix
  (TanStack Start's file-based-routing convention; `index.rs` is the
  `/playground` index route -> `PlaygroundIndex`), aggregated by
  `pages/playground/mod.rs`. dioxus-router has no file-system route
  generation, so `routes.rs` still declares every route explicitly.
- `src/pages/responsive_flow.rs`, `src/pages/responsive_overlay.rs` — the
  shell-free `/responsive/*` viewport-harness fixtures, kept at this top
  level (not under `pages/playground/`) since their routes render outside
  every layout.
- `src/routes.rs` — the `Route` enum (`dioxus-router`, requires the
  `router` Dioxus feature), `nav_items()`, `SiteLayout` (the site-wide
  header: logo, Docs/Playground/GitHub nav, theme controls), and
  `PlaygroundLayout` (the playground's own nav sidebar + theme
  customization tray, nested inside `SiteLayout` under `/playground/*`).
- `src/main.rs` — the `App` entrypoint: asset links, document title, and
  mounting `Router::<Route> {}`.
- `src/components/cta_link.rs` — a plain anchor for cross-app/external
  links that neither `Button` (native `<button>`, no `href`) nor
  `NavigationMenuLink` (requires a `NavigationMenu` ancestor) can serve
  standalone, used by the landing page.
- `src/components/demo.rs` — the shared `Demo` wrapper each playground page
  uses to render its component under a heading.
- `src/components/controls.rs` — small bound prop-controls
  (`BoolControl`/`TextControl`/`SelectControl`) playground pages use for
  live props.
- `assets/web/` — the site's branded favicon, touch-icon, and logo assets,
  linked from the Dioxus document shell and used in the navigation.
- `src/components/ui/` — generated by `adico add`; do not hand-edit the
  `// adico:start` / `// adico:end` managed region in `components/mod.rs`
  (hand-authored `pub mod cta_link;`/`pub mod demo;`/`pub mod controls;`
  lines live outside that region in the same file).

## Wiring a fresh app for Tailwind (manual today)

`adico init` / `adico add` writes the CSS theme tokens but does **not** yet
wire the following two steps automatically — do them by hand once per app:

1. Add a project-root `tailwind.css` (compile *input*, not the generated
   output) containing at minimum:

   ```css
   @import "tailwindcss";
   @source "./src";
   /* adico:theme:start */
   ...
   /* adico:theme:end */
   ```

   `dx serve`/`dx build` auto-detects this file and compiles it into
   `assets/tailwind.css` (generated output — never hand-edit that file).
2. Link the compiled stylesheet and enable the Dioxus `document` feature:

   ```rust
   const TAILWIND_CSS: Asset = asset!("/assets/tailwind.css");
   // in your root component:
   document::Stylesheet { href: TAILWIND_CSS }
   ```

   ```toml
   dioxus = { version = "=0.7.9", features = ["document", ...] }
   ```

Without both steps, every installed component renders as unstyled semantic
HTML.

## Theme combinations

The navigation contains a session-only customization tray. Use primary,
secondary, and tertiary palette presets, or generate a fresh combination, then
switch between light and dark appearance. The tray also exposes every semantic
variable installed by adico: surfaces, role/foreground pairs, border/input/
ring/radius, and sidebar values. It changes shared CSS variables rather than
passing theme props to copied component source, so every route is a live
consumer-theme check. Light and dark customizations are kept separately.

## Running

```sh
dx serve --platform web
```
